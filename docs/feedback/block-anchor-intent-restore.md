# 결정 요청 — block/anchor를 원 의도대로 되돌릴 것인가 (4개 갈래)

사용자 지적: **"42 line 제한으로 지식의 최소 단위인 block(annotation)을 형성한다는 것과, block
단위를 확률기반 엣지로 연결하여 구조적인 지식을 형성하는 skeleton(anchor)에 대한 활용이 의도와는
많이 다르게 구현된 것 같다."**

충실도 감사(`docs/verify/block-anchor-intent-fidelity.md`) 결과 **지적이 실측으로 지지된다**:
의도 5요소 중 **일치 0 / 부분 1 / 다른 것으로 대체 2 / 미표현 2**. 판정 한 줄 —
*"사용자가 말한 skeleton은 현재 그래프에 실재하지 않는다."*

## 확정된 진단 (원문·커밋으로 재확인)

| # | 의도 | 현재 |
|---|---|---|
| G1 | 42-line이 **지식 단위를 형성**하는 장치 | 260-token **상한 린트**만. 하한 130은 권고(미강제) → 큰 것은 거부하나 **분해를 강제하지 않음**. cap의 근거도 granularity에서 **검색 정밀도**로 교체됨 |
| G2 | **block = 지식의 최소 단위**(1급) | block에 해당하는 **어휘 자체가 없음**. block은 "노드의 텍스트"일 뿐 → **schema 확장 트리거** |
| G3 | block **↔** block **확률** 엣지 | node↔node **가중 엣지 어휘 없음**. 전환점: 원 진단 "edge-level confidence 부재"가 해법 번역 과정에서 **부착점 가중(n-ary anchor)** 으로 대상이 바뀜 → **schema 확장 트리거** |
| G4 | backbone = **확률적 그래프**(ConceptScheme + confidence 가중) | `skos:broader` 70·`tagged` 224·facet 84 **전부 crisp**. 승인 계획 ①~④에 backbone 엣지 가중 단계가 **애초에 없었음** |
| G5 | anchor = backbone 위의 구조적 위치 | **동음이의 3중**. 계보: 그래프 anchor 先(전사 08-27 → 커밋 08-28 01:06), 편집기 텍스트 anchor 後(08-28 12:48) |

현재 실재하는 것: crisp 개념 taxonomy(깊이 2) + anchor 7개의 성긴 이분 별 구조(3노드→개념 6개,
projection 전면 제외, 소비 0줄). 유일한 unit↔unit 직접 엣지는 **그래프 밖** 링크 평면 7건(crisp).
→ **"확률 + block↔block"을 갖춘 표현은 어느 층에도 없다.**

## 결정 1 — 확률 엣지를 어디에 둘 것인가 (G3·G4의 핵심)

- **[앵커 확장]** (권고) `ho:anchorTarget`의 range를 `ho:Concept` → **모든 component**로 넓힌다.
  그러면 기존 n-ary 구조(대상 + confidence + 부착 노드)가 **그대로 node↔node 가중 엣지**가 된다.
  스키마 변경 최소(range 1곳 + shape), 이미 있는 기계(AnchorShape·prefix·롤업)를 재사용.
  ⚠ 단서: 지금 anchor는 팩 오염 때문에 **projection에서 전면 제외**돼 있다. 앵커가 뼈대가 되면
  **엣지로는 순회하되 노드로는 admit하지 않는** 처리로 바꿔야 한다(별도 작업 1건).
- **[엣지 가중 신설]** `skos:broader` 등 backbone 엣지 자체에 confidence를 얹는 새 어휘를 만든다
  (RDF 특성상 reification 또는 별도 n-ary가 필요 → 결국 앵커와 같은 모양이 된다). 원 제안 문면에
  가장 가깝지만 앵커와 **두 개의 같은 기계**가 생길 위험.
- **[현행 유지]** crisp taxonomy + 부착점 가중을 유지한다. 사용자의 원 의도는 미실현으로 남는다.

## 결정 2 — block을 1급으로 세울 것인가 (G1·G2)

- **[하한 강제]** (권고) block 클래스는 만들지 않고 **노드를 block으로 간주**하되, 지금 권고인
  하한(130 token)을 **린터 게이트로 승격**한다. 그러면 42-line의 원 기능("한 단위에 한 덩어리")이
  상한·하한 양쪽으로 서고, 지식을 **나누도록 강제**된다. 스키마 변경 0.
  ⚠ 대가: 현재 하한 미달 노드가 다수다(예: 짧은 개념·도구). 일괄 확장은 밀도 목표에 역행하므로
  **적용 범위(어느 클래스에 걸 것인가)를 함께 정해야 한다.**
- **[block 1급화]** `ho:Block`(또는 Annotation) 클래스를 신설해 "지식 단위 텍스트"를 노드와 분리한다.
  의도에 가장 충실하나 **재모델링 규모가 크다**(모든 텍스트 보유 노드의 재배치 + 렌더·검색 파급).
- **[현행 유지]** 상한만 강제한다.

## 결정 3 — anchor 이름 충돌 정리 (G5)

- **[편집기 개명]** (권고) 계보상 그래프 anchor가 먼저이므로 **편집기 쪽을 `selector` 또는
  `position anchor`로 개명**한다. 병행 세션이 자기 lane 몫으로 수행하겠다고 확인했다.
- **[그래프 개명]** 중앙 `ho:Anchor`를 다른 이름으로. 이미 land된 스키마·shape·prefix를 건드린다.
- **[현행 유지]** 동음이의를 문서로만 구분한다.

## 결정 4 — 그래프 밖 링크 평면을 어떻게 할 것인가

- **[평면 유지 + 확률 부여]** 링크 평면은 그대로 두되 엣지에 confidence를 싣는다(병행 세션 몫).
- **[그래프로 흡수]** 링크 평면의 unit↔unit 엣지를 중앙 그래프로 들인다 — 결정 1과 겹치므로
  결정 1이 [앵커 확장]이면 이쪽은 불필요할 수 있다.
- **[현행 유지]** 평면 결합 용도로만 둔다.

> 결정 1을 먼저 정하면 결정 4는 자동으로 좁아진다. 결정 2·3은 1과 독립이다.

## 사용자 결정 (2026-08-28, 구체화 문답 2라운드)

grill-me 규약에 따라 orchestrator가 모호점을 질의하고 사용자가 확정한 내용:

1. **cap 초과 시 게이트** = **실패 + 분할 지시**. 자르지 않는다. 메시지는 "의미 단위로 나누라"이고
   지식 손실 없이 분해가 강제된다.
2. **분할된 조각의 연결** = **확률 엣지로만**. "같은 지식의 부분"을 위한 전용 술어를 따로 만들지
   않고, 확률 연결의 **한 종류**로 표현한다.
3. **확률 엣지의 성격** = 단순 단위↔단위 연결이 아니라 **다양한 구조의 지식을 표현할 수 있는
   확률적 연결**. 즉 관계의 **종류(typed)** 와 **가중(weighted)** 을 함께 갖는다.
4. **최소 크기(하한)** = **강제하지 않는다**. 단위를 정하는 기준은 크기가 아니라 응집이다.
5. **기존 crisp 관계** = **전부 확률 연결로 이전**하며, **확률은 퍼지 방식으로 도입**한다
   (`skos:broader` 70 · `tagged` 224 · alternativeOf · overlapsWith 포함).
6. **확률값의 근거** = **측정에서 산출을 기본**으로 하되 **사람이 확인·수정할 수 있게** 한다.

### orchestrator 주석 (실행 시 반드시 지킬 제약)

- **유사도 단독 측정은 근거로 쓸 수 없다** — 이번 사이클 실측에서 문장 교체와 부분 삭제가
  문자열상 구분 불가임이 확인됐다(`anchor-move` 계열 실측). 측정 기반을 설계할 때 유사도만으로
  값을 만들면 같은 함정을 그래프에 새긴다.
- **값의 출처를 데이터로 남긴다** — 측정 산출인지 사람이 확정·수정한 값인지 구분되지 않으면
  사람의 교정이 다음 재측정에 덮여 사라진다.
- **선언 전용 개체는 검색 중립이 아니다** — anchor 저작에서 실측된 대로, 개체가 존재하는 것만으로
  팩이 오염된다. 확률 연결은 **엣지로는 순회하되 노드로는 팩에 admit되지 않아야** 한다.
- **규모**: `broader` 70 + `tagged` 224 + alternativeOf/overlapsWith를 전부 옮기는 것은 그래프·검색·
  shape·린터·렌더·연합 recipe 전반을 건드리는 대규모 이전이다. **1단계(스키마 + 수직 슬라이스)
  → 검증 → 2단계(대량 이전) → 검증 → 3단계(도구·게이트)** 로 나눈다. 각 단계는 이전 단계의
  판정 통과를 진입 조건으로 한다.
