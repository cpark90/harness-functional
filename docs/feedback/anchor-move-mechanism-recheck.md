# 재질의 — 승인된 (c) CRDT move가 현 스택에서 막혔습니다

`anchor-move-recovery-tradeoff.md`에서 **(c) CRDT의 진짜 move 연산**을 승인해 주셨습니다.
그런데 그 항목에 **승인 이후 붙은 선행 조사**가 (c)의 전제를 무너뜨립니다. 실행 전에 한 번만
다시 여쭙습니다 — 승인을 뒤집으려는 것이 아니라, **같은 목표를 어느 경로로 이룰지**입니다.

## 조사가 말하는 것 (요약, 원본은 위 항목의 "(c) 선행 조사 결과")

- **현 스택(Yjs)에서 (c)는 불가**: Yjs는 **v14에서 move 지원을 중단**하기로 했고(복잡도·낮은
  사용률), v14.0.0-1의 move 구현에는 **배열 corruption 이슈**가 보고됐습니다. v13의 move는
  실험 단계로 남아 있고 공식 권장은 "기존 프리미티브로 우회 구현"입니다.
- **(c)를 하려면 스택 교체**: Loro는 movable list가 1급 연산이고 공식 ProseMirror 바인딩이
  있습니다. 대신 앵커 엔진의 CRDT 교체(RelativePosition 대체·영속 포맷 변경·Phase 1 스위트
  전면 재검증)가 따라옵니다 — 지금까지 쌓은 검증 자산 대부분을 다시 만들어야 합니다.
- **(b)가 당초보다 쌈**: 안정 블록 id는 **Tiptap UniqueID 확장이 MIT(무료)** 로 이미 있습니다.
  기존 문서는 1회성 id 부여, 외부 문서는 id가 없어 현행 orphan 동작으로 자연 강등됩니다.
  스택 교체가 없으므로 Phase 1·C1·C1b 검증 자산이 그대로 유지되고, **이동 복구와 오해소 0을
  동시에** 얻는다는 점은 (c)와 같습니다.

## 왜 자동으로 (b)로 바꾸지 않았나

승인된 것은 (c)이고, 조사는 그 뒤에 붙었습니다. "비용이 크니 알아서 (b)로 했다"는 것은
승인 게이트를 우회하는 일이라 하지 않았습니다. 다만 (c)를 문자 그대로 실행하면 **스택 교체
웨이브**가 되므로, 그 규모를 승인 없이 착수할 수도 없습니다.

## 선택지

- **(a) (b)로 전환 (권고)** — Tiptap UniqueID(MIT)로 안정 블록 id를 도입한다. 목표(이동 복구
  + 오해소 0)는 (c)와 동일하게 달성되고, 검증 자산이 유지된다. 규모: 앵커 레코드에 블록 id
  selector 추가 + 기존 문서 마이그레이션 + 스위트 재측정.
- **(b) (c) 유지, Loro 스택 교체 착수** — CRDT 층을 Loro로 옮긴다. 정체성이 CRDT 자체에서
  보존되므로 가장 근본적이지만, 앵커 엔진 재작성 + Phase 1 스위트 전면 재검증이 따른다.
- **(c) 둘 다 지금은 보류** — 현행(이동 시 orphan, 오해소 0)을 유지하고, 다른 lane을 먼저
  진행한다. 지금도 안전한 상태이며 orphan은 사용자에게 명시 표시된다.
