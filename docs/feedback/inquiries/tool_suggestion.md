# 지식 평면 분리형 에이전트 문서편집기 — 설계 제안

> 상태: 개정 초안 v0.2 — 하단 §검토의 필수 A·B + 보완 C·D·E를 본문에 반영 (`[v0.2]` 마커)
> 작성일: 2026-08-27 (v0.2 반영 동일)
> 범위: 아키텍처 방향성 제안 및 기술 선택 근거. 상세 API 명세는 후속 문서.

## 1. 배경

자율 에이전트가 개발·설계 작업에 투입되면서, 에이전트가 읽고 쓰는 산출물의 관리 방식이 병목이 되고 있다. 현재 대부분의 코딩 에이전트는 모든 산출물을 "파일"이라는 단일 추상으로 다루며, 그 결과 성격이 전혀 다른 지식들이 하나의 컨텍스트 윈도우에 무차별적으로 적재된다.

구체적으로 다음 네 종류의 지식이 구분 없이 섞인다.

- **주석 / 리뷰 코멘트** — 특정 위치를 겨냥한, 수명이 짧고 사회적으로 해소되는 지식
- **설계 결정 / 아키텍처 문서** — 근거와 논증으로 구성되며, 논박 가능한 지식
- **데이터 프로토콜 / 스키마** — 기계적으로 검증 가능한 계약
- **인터페이스 / 타입 시그니처** — 컴파일러가 판정하는 계약

이들은 **"맞다"고 판정되는 메커니즘이 근본적으로 다르다.** 그럼에도 같은 컨텍스트에 평평하게 놓이면, 에이전트는 컴파일러가 보증하는 사실과 아직 논박 중인 주장, 이미 해소된 과거 논의를 동일한 신뢰도로 취급하게 된다.

관심사 분리(SoC) 위반이 에이전트 아키텍처에서 컨텍스트 로트를 넘어 실제 사고로 이어진 사례들이 보고되고 있으며, 본 제안은 그 분리 축을 "작업 단계"가 아닌 "지식 종류"로 옮기는 것을 목표로 한다.

## 2. 문제 정의

### 2.1 지식 종류별 특성

| 지식 종류 | 진리 판정 방식 | 변경률 | 원자 단위 | 안정적 식별자 |
|---|---|---|---|---|
| 주석 | 사회적 합의 (해소/승인) | 매우 높음 | 스레드 | 앵커 (selector) |
| 설계 결정 | 논증의 타당성 (논박 가능) | 낮음 | 결정(decision) | 결정 ID |
| 데이터 프로토콜 | 스키마 검증·호환성 검사 | 낮음 | 메시지/필드 | 스키마 경로 |
| 인터페이스 | 타입 체커 (결정론적) | 중간 | 시그니처 | 심볼 ID |
| 지식 그래프 `[v0.2 A]` | SHACL + validate (결정론) | 낮음 | individual (노드) | IRI (`id:`/`core:`) |

`[v0.2 A]` **지식 그래프 평면**: 이 프로젝트의 1급 지식인 하네스 온톨로지(TBox)+KG(ABox).
승인된 backbone+anchored-annotation 아키텍처(`docs/feedback/annotation-backbone-architecture.md`,
approved)의 anchor 대상이 바로 이 평면의 IRI다 — 도구와 그래프를 잇는 접점.

식별자 열이 특히 중요하다. **각 지식은 자기 도메인에서 이미 안정적인 식별자를 갖고 있는데**, 파일 추상은 이를 전부 "경로 + 줄 번호"로 붕괴시킨다.

### 2.2 기존 접근의 한계

현재 컨텍스트 격리 기법은 모두 **"누가 / 언제"** 축으로 나뉜다.

- 서브에이전트 패턴: 각 서브에이전트가 독립 컨텍스트 윈도우, 전용 시스템 프롬프트, 제한된 툴 권한을 가짐
- 단계 분리: 리서치 → 플래닝 → 구현 → 검증
- 프레임워크 수준 지원: Google ADK의 `include_contents` 노브로 호출자 컨텍스트 전달량 제어

이 격리는 유효하지만 **지식 종류 축은 다루지 않는다.** 결과적으로 단일 구현 서브에이전트의 컨텍스트 안에 설계 근거·인터페이스 시그니처·리뷰 코멘트·스키마가 그대로 뒤섞인다. 원래의 커플링이 서브에이전트 내부에서 재현된다.

## 3. 선행 기술 검토

### 3.1 인접 연구가 다루는 분리 축

| 연구 / 제품 | 분리 대상 | 분리 축 |
|---|---|---|
| Tiptap AI Toolkit | 콘텐츠 vs 구조(스키마) | 표현 계층 |
| SWE-Edit | 탐색 vs 편집 실행 | 작업 단계 |
| CAPRA | 평가 차원별 에이전트 | 분석 관심사 |
| **본 제안** | **주석·설계·프로토콜·인터페이스** | **지식 종류** |

앞의 세 연구는 모두 "같은 종류의 지식을 어떻게 다룰까"를 다루며, 본 제안은 그 위의 직교 축이다. 따라서 배타적이지 않고 **중첩 적용 가능**하다.

### 3.2 Standoff 주석 모델

마크업과 대상 텍스트를 분리 저장하는 standoff 기법은, 마크업 속성 집합이 텍스트의 서로 다른 측면을 각각 기록하고 필요 시 재결합되는 divide-and-conquer 접근을 가능하게 한다. 본 제안의 주석 평면이 정확히 이 구조다.

참고 대상:

- **W3C Web Annotation Data Model** — Selector 다중화 패턴. `TextQuoteSelector`(exact/prefix/suffix) + 위치 오프셋 + 구조 경로를 동시 저장하여 하나가 깨져도 나머지로 복구. 전송 프로토콜을 규정하지 않고 데이터 모델만 정의하는 설계도 참고할 만하다.
- **STAM (Stand-off Text Annotation Model)** — RDF·TEI 등 복잡한 모델에 의존하지 않고 최소 공통분모만 정의한 뒤 어휘는 사용자에게 위임. 인라인 마크업 XML을 순수 평문 + standoff 주석으로 분해하는 임포터 제공. **메커니즘은 고정하되 어휘는 도메인에 위임**한다는 설계 결정을 차용한다.
- **STAM transposition 확장** — 서로 다른 리소스 간 동일 텍스트 부분 연결. 교차 평면 링크에 응용 가능.

**알려진 약점:** 기저 텍스트와 마크업이 동시에 변할 때의 앵커 드리프트. 텍스트와 별개로 standoff 속성 집합을 갱신하는 알고리즘이 제안되어 있으며, 4.4절에서 이에 대한 대응을 다룬다.

### 3.3 MBSE의 View / Viewpoint

본 제안의 "평면별 컨텍스트" 개념은 시스템공학 쪽에 이미 형식화되어 있다.

- SysML은 view와 viewpoint 개념을 갖고, view는 반드시 viewpoint에 부합해야 하며 viewpoint가 그 view를 구성·사용하는 규약과 규칙을 규정한다. 단, **viewpoint를 어떻게 명세할지에 대한 방법은 규정하지 않는다** (5.2절 리스크 참조).
- RM-ODP(ISO/IEC)는 분산처리 시스템을 5개 viewpoint로 규정한 도메인별 사례.
- 핵심 정의: **view는 하나 또는 여러 기저 모델의 투영이며, 이해관계자에게 자신의 작업에 필요한 본질적 정보만 제시한다.** "이해관계자"를 "에이전트"로 치환하면 본 제안과 동일하다.

구현 참고: 상용 MBSE 도구(CATIA Magic/Cameo)는 모델을 질의하는 표현식으로 뷰를 **동적 생성**하고, 모델 변경 시 뷰를 자동 재구축하며, 뷰 정의를 라이브러리에 저장해 재사용한다. **뷰를 저장하지 않고 매번 조립한다**는 원칙을 그대로 채택한다.

하이브리드 언어서버 연구도 같은 결론에 도달했다 — 서로 다른 뷰를 지원해야만 모델의 각 부분과 서로 다른 투영·분석 결과를 적절히 표시할 수 있으며, 일부 연산은 단일 모델 시각화와 본질적으로 양립 불가능하다.

### 3.4 툴 스코핑

전문화된 툴이 늘면 툴별 추론 부담은 줄지만 탐색해야 할 액션 공간은 커진다. 이 트레이드오프에 대해 Prometheus의 노드별 툴 스코핑과 AutoCodeRover의 단계 분리는 **매 결정 지점에서 전체 툴셋을 제시하는 대신 보이는 툴을 제한**하는 전략을 취한다. 본 제안은 이를 평면 축으로 전용한다.

## 4. 제안 아키텍처

### 4.1 개요

```
                에이전트 작업 컨텍스트
                  (과업별로 조립됨)
                         ↑
            투영 계층 (view / viewpoint)
          질의로 뷰 생성 — 저장하지 않음
                         ↑
    ┌──────────┬──────────┬──────────┬──────────┬──────────┐
    │   주석   │ 설계 결정│ 프로토콜 │인터페이스│지식그래프│
    │사회적합의│ 논박가능 │스키마검증│ 타입검사 │SHACL검증 │
    └──────────┴──────────┴──────────┴──────────┴──────────┘
                         ↓
       링크 평면 — 평면 간 유일한 결합점
         standoff selector + 타입된 관계
```

### 4.2 불변식

아키텍처를 지탱하는 세 가지 규칙.

**I1. 평면 간 직접 참조 금지**
설계문서가 인터페이스 시그니처를 인라인으로 인용하지 않는다. 링크만 건다. 인용을 허용하는 순간 동기화 문제가 부활하고 커플링이 복원된다.

**I2. 뷰는 저장하지 않고 질의로 조립**
과업별 컨텍스트는 영속 아티팩트가 아니라 매번 질의로 생성되는 투영이다. 이렇게 하면 평면 갱신과 뷰 갱신 사이의 동기화 문제가 원천적으로 사라진다.

**I3. 평면마다 다른 쓰기 규약**

| 평면 | 커밋 조건 |
|---|---|
| 인터페이스 | 타입 체크 통과 |
| 프로토콜 | 스키마 검증 + 하위 호환성 검사 통과 |
| 설계 결정 | 상위 결정과의 모순 없음 **판정 기록 존재** `[v0.2 D]` (기계 판정 불가 — §7 리스크 참조) |
| 주석 | 검증 없음. 단, 해소 상태(open/resolved) 필수 |
| 지식 그래프 `[v0.2 A]` | SHACL(shapes) + `validate.py` 하드 축 + webui `plan_upsert` 게이트 통과 (anchor 없는 annotation 저장 거부 포함) |

### 4.3 링크 평면

평면 간 유일한 결합점. 링크는 **타입을 가지며**, 허용되는 타입 집합을 소수로 고정한다 (5.3절 리스크 참조).

초안 링크 타입 `[v0.2 B: 기존 어휘 재사용으로 정렬]`:

| 타입 | 출발 | 도착 | 의미 | 어휘 근거 |
|---|---|---|---|---|
| `realizes` | 인터페이스 | 설계 결정 | 이 시그니처가 이 결정을 구현 | 신설 (기존 등가 없음) |
| `constrainedBy` | 인터페이스 | 프로토콜 | 이 시그니처가 이 스키마에 제약됨 | **`ho:constrainedBy` 재사용** (방향 정렬) |
| `supersedes` | 설계 결정 | 설계 결정 | 결정 대체 — **설계결정 평면 내부 한정** | 신설. **지식 그래프 평면 사용 금지**: B9 결정으로 그래프에서 폐기=제거(추적성은 git/docs), supersedes 의미를 그래프에 재도입하면 재드리프트 |
| `hasTarget` | 주석 | 임의 | 주석 대상 | **W3C `oa:hasTarget` 재사용**; 그래프 개체 대상이면 `ho:tagged`와 정렬 |
| `derivedFrom` | 프로토콜 | 설계 결정 | 스키마의 근거 | **`ho:derivedFrom` 재사용** |

`[v0.2 B]` **어휘 규칙**: 링크 타입은 신설 전에 기존 어휘(`ho:`/`oa:`/`dct:`)를 재사용한다
(golden rule 2의 도구판 — 근사동의어 신설 금지). 미정의 타입 금지 원칙은 유지.

### 4.4 평면별 앵커

각 평면은 **자기 도메인의 네이티브 식별자를 유지한다.** 이것이 이 설계의 핵심이다.

| 평면 | 앵커 | 근거 |
|---|---|---|
| 주석 | ProseMirror 플러그인 상태 + Yjs `RelativePosition` | 편집 후에도 위치 자동 재정렬 |
| 설계 결정 | Tiptap 문서 + 노드 ID | 산문 구조에 자연스러움 |
| 인터페이스 | LSP 심볼 ID | 함수의 정체성은 텍스트 위치가 아니라 심볼. 리팩터링으로 파일 간 이동해도 동일 |
| 프로토콜 | 스키마 경로 (`Msg.field`) | 스키마 레지스트리의 네이티브 식별자 |
| 지식 그래프 `[v0.2 A]` | IRI (`id:`/`core:` — ONTOLOGYSTYLE §2a) | 그래프 개체의 안정 식별자; `retrieve.py`/`materialize.py`가 이미 소비하는 네이티브 앵커 |

## 5. 기술 선택 — Tiptap / ProseMirror

### 5.1 채택 근거

ProseMirror는 standoff의 최대 난점인 **앵커 재정렬을 이미 프로덕션 수준으로 해결**해 두었다.

- **Step / StepMap / Mapping** — 모든 변경이 Step으로 표현되고, 각 Step이 이전 위치를 새 위치로 옮기는 맵을 생성. "텍스트와 별개로 앵커 집합을 갱신하는 알고리즘"이 문서 모델에 내장되어 있다.
- **Decoration / DecorationSet** — Decoration은 문서의 일부가 아니라 플러그인 상태에 별도로 존재한다. `DecorationSet.map(mapping, doc)` 한 번으로 편집 후 앵커가 자동 재정렬된다. 이것이 정확히 "콘텐츠와 분리된 레이어"다.
- **플러그인 상태의 `apply(tr, state)`** — 플러그인마다 독립 상태를 갖고 모든 트랜잭션에 대해 자기 방식으로 갱신. **플러그인 N개 = 레이어 N개**가 그대로 성립한다.

Tiptap 계층의 추가 이점:

- JSON 기반 콘텐츠 모델 + 스키마 검증. 문서를 평문으로 취급할 때의 전체 재생성 문제(느림, 토큰 낭비, 서식 손실)를 회피한다.
- AI Toolkit이 문서 구조 자체를 AI에 노출. 최소 툴 세트는 `tiptapRead` / `tiptapEdit` / `tiptapReadSelection` 3개로 억제되어 있다.
- 코멘트 스레드가 콘텐츠와 별개로 제공되며, `getThreads` / `editThreads`는 **기본 비활성**. 주석 평면이 기본적으로 컨텍스트에 들어오지 않는다는 뜻으로, 본 제안의 방향과 일치한다.
- Server AI Toolkit으로 에디터 세션 없이 서버 측 배치 처리 가능.
- 변경 승인 레이어(decoration 또는 tracked changes)와 tool call 스트리밍 내장.

### 5.2 명시적 안티패턴 — 레이어를 mark로 구현하지 말 것

가장 흔한 오설계이며 반드시 회피해야 한다.

ProseMirror mark로 레이어를 표현하면:

1. mark는 **문서 안에** 저장된다. standoff가 아니라 인라인 마크업으로 회귀한다.
2. 스키마에 mark 타입을 선언해야 하므로, 레이어 추가마다 **문서 스키마가 오염**된다. 커플링이 스키마 레벨에 생긴다.
3. mark는 인라인 전용이다. "이 섹션 전체가 ADR-014를 실현한다" 같은 블록·구조 단위 링크를 표현할 수 없다.

**규칙: 레이어는 플러그인 상태 + Decoration으로, 영속화는 별도 레코드로. 문서 스키마는 순수 콘텐츠만 알아야 한다.**

### 5.3 Tiptap 적용 범위 한정

Tiptap은 **산문 계열 두 평면의 앵커 엔진**으로만 사용한다.

| 평면 | Tiptap 역할 |
|---|---|
| 주석 | 전담 (강점 영역) |
| 설계 결정 | 전담 (강점 영역) |
| 인터페이스 | 없음 — 링크 대상으로만 참여 |
| 프로토콜 | 없음 — 링크 대상으로만 참여 |
| 지식 그래프 `[v0.2 A]` | 없음 — 링크 대상으로만 참여 (쓰기는 webui `plan_upsert` 게이트 경유) |
| 링크 | 없음 — 독립 저장소 |

범위를 한정하는 이유:

**(a) ProseMirror는 단일 루트 트리다.** position mapping은 한 문서 내부에서만 동작한다. 설계문서 A와 인터페이스 정의 B가 별개 문서면, A의 편집이 B의 앵커를 갱신해주지 않는다. 교차 문서 링크는 공짜 구간 밖이다.

**(b) 인터페이스·프로토콜은 산문이 아니다.** 시그니처의 정체성은 텍스트 위치가 아니라 심볼이다. 이를 ProseMirror 문서에 넣는 것은 범주 오류이며, LSP/tree-sitter 심볼 식별자가 올바른 앵커다.

**(c) 평면별 검증 규칙은 스키마가 담지 못한다.** ProseMirror 스키마는 구조 제약(어떤 노드가 어떤 노드를 담는가)만 표현한다. "이 필드 변경이 v3와 하위 호환인가"는 표현 불가다. I3의 쓰기 규약은 `filterTransaction` / `appendTransaction` 등 트랜잭션 게이트로 별도 구현해야 한다. **스키마가 이 일을 해줄 것이라 기대해서는 안 된다.**

### 5.4 앵커 영속화

Decoration의 위치는 절대 오프셋이므로 세션 밖으로 나가면 무의미하다. 저장 시 상대 위치로 변환해야 한다.

협업·오프라인 편집까지 고려하면 **Yjs `RelativePosition` (y-prosemirror)** 이 표준 답이다. 이 경우 오프라인 편집 후 병합에서도 앵커가 살아남는다.

## 6. 툴 표면 설계

### 6.1 핵심 원칙 — 저장 레이어링 ≠ 컨텍스트 레이어링

**가장 중요한 함정이다.** 데이터 모델에서 레이어를 나눠도, 읽기 툴이 여전히 문서 전체를 한 번에 반환하면 **원래 목표였던 컨텍스트 분리는 전혀 달성되지 않는다.** 저장소만 깔끔해지고 에이전트 컨텍스트는 그대로 뒤섞인다.

따라서 툴 표면이 반드시 평면 축으로 파라미터화되어야 한다.

### 6.2 평면별 툴 스코핑

3.4절의 노드별 툴 스코핑을 평면 축에 적용한다. **현재 평면에서 유효한 툴만 노출한다.** 프로토콜 평면에 있을 때 `resolve_comment`가 보여서는 안 된다.

권장: 평면당 3~5개 툴, 총 평면 수 4~6개 상한 (5.3절 리스크 참조).

### 6.3 읽기 응답의 평면별 형태

같은 `read`라도 반환 형태가 해당 평면의 원자 단위를 따라야 한다.

| 평면 | 기본 읽기 응답 |
|---|---|
| 설계 결정 | 결정 단위 요약 (결정 ID + 결론 + 상태) |
| 주석 | 미해소 스레드만 |
| 프로토콜 | 변경된 필드 diff |
| 인터페이스 | 시그니처 목록 (본문 제외) |
| 지식 그래프 `[v0.2 A]` | 요청-스코프 컨텍스트 팩 (`retrieve.py` — 예산 상한·anchor 영역당 대안 1선별) |

계층적 확장(요약 → 필요 부분만 펼침)을 기본으로 하여 읽기 비용을 통제한다.

### 6.4 교차 평면 일관성 담당

평면을 나눴다면 **평면 간 모순을 잡는 역할이 별도로 존재해야 한다.**

CAPRA의 ConsistencyManager 패턴을 차용한다 — 모든 평면의 변경을 읽고 중복을 병합해 최종 승인을 내리는 별도 에이전트를 두고, **퍼지 매칭으로 인용된 발견이 원본과 실제 일치하는지 결정론적으로 검증**한다. 에이전트가 "N절을 수정했다"고 주장할 때 실제 diff와 대조하는 용도로 그대로 적용 가능하다.

## 8. 단계별 로드맵

**Phase 0 — 기존 lane 형식화 (신규 구현 없음)** `[v0.2 E]`
이 repo에 이미 있는 각 평면의 원시 구현을 매핑하고 재사용 경계를 명세한다: 주석 평면 ≈

보고, 프로토콜 ≈ TBox+SHACL, 지식 그래프 뷰 ≈ `retrieve.py`, 쓰기 게이트 ≈ webui
`plan_upsert`. 백지 구현 대신 이 lane들의 형식화에서 시작해 검증 비용을 줄인다.

**Phase 1 — 앵커 엔진 검증**
ProseMirror 플러그인 하나 = 레이어 하나 구조로 주석 평면 프로토타입. Yjs RelativePosition 기반 영속화. 편집 후 앵커 생존율 측정.

**Phase 2 — 산문 평면 2종**
설계 결정 평면 추가. 두 평면 간 링크 저장소와 `targets` / `supersedes` 링크 타입 구현.

**Phase 3 — 코드 평면 연결**
LSP 심볼 ID 및 스키마 경로를 링크 대상으로 편입. 실제 편집은 기존 파일 도구에 위임하고 링크 무결성만 관리.

**Phase 4 — 툴 스코핑 및 투영**
평면별 툴 노출 제어, 평면별 읽기 응답 형태, 질의 기반 뷰 조립. `[v0.2 C]` 추가: 승인 항목
(A)의 두 장치를 이 단계에서 강제한다 — **annotation 크기 cap**(단위 line vs token은 미결,
`lint_uniformity.py`에 검사 추가) + **anchor 영역당 대안 1선별**(`retrieve.py`와 동일 선별
규칙 공유 — 도구/retrieve 이중 구현 금지, determinism 게이트 유지).

**Phase 5 — 일관성 검증**
교차 평면 모순 검사 및 결정론적 diff 대조.
