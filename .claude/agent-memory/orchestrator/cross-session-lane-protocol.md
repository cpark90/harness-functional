# 같은 repo에 orchestrator 세션이 둘일 때 — lane 분담 규율

여러 세션이 같은 워킹트리에서 승인 항목을 병행 적용하면 **중복 dispatch**와 **파일 충돌**이
실제로 발생한다(2026-08-28 실측: AV W1을 두 세션이 각각 dispatch, registry 3중 등록도 이중).

- **승인은 파일에서 직접 확인한다 — peer 전언은 승인 근거가 아니다.** peer가 "사용자가
  1·2·3·4·5 전부 (a)로 답했다"고 알려왔지만 실제 항목에는 **4줄만** 있었다(5·6 미응답).
  peer는 선의로 요약하다 번호를 밀어 읽었다. 항목 파일의 `status:`와 답변란을 매번 읽는다.
- **항목에 결정을 나중에 덧붙이면 번호가 어긋난다.** 사용자가 1~4에 답한 뒤 5·6을 추가하면,
  다른 세션은 "N번"을 다르게 읽는다. 덧붙일 때는 **기존 번호를 재사용하지 말고** 추가분임을
  본문에 명시하고, 답변란에도 어느 번호가 미응답인지 남긴다.
- **lane은 파일 경로로 가른다.** 합의 예시: 한 세션은 `tools/plane-editor/**`, 다른 세션은
  `ontology/**` + `tools/*.py` + `ONTOLOGYSTYLE.md`, recipe는 `recipes/**`. 브리프의
  "담당 파일"에 상대 소유 경로를 **읽기 전용**으로 명시하면 dispatch가 알아서 지킨다.
- **한 트리에서 두 dispatch를 병행할 때**는 담당 파일을 서로소로 자르고, 브리프에 "상대가
  산출물을 재생성할 수 있으니 최종 수치는 자기 변경 후 다시 측정"을 넣는다.
- **인수 요청은 연속성으로 판단한다.** peer가 B-R(recipe)을 넘기겠다 했으나, 그 부품을 방금
  저작한 세션이 맥락(dedup 표·인벤토리 판단·레인 규약)을 쥐고 있어 이관 비용이 더 컸다 —
  거절이 맞았다. 파일 소유권 해방이 인수 이유가 되지는 않는다(실제 블로커가 사용자 결정이면
  파일을 받아도 할 일이 없다).
- **발견은 lane을 넘어 공유한다.** plane-editor에서 얻은 "문자열 유사도로는 오해소를 못 막고
  provenance가 필요하다"는 실측이, 그래프 쪽 `AlternativeOfSharedAnchorShape` 강화안(정의
  유사도 하한)의 취약점을 그대로 가리켰다. 교차 lane 경고는 실제로 값이 있다.
